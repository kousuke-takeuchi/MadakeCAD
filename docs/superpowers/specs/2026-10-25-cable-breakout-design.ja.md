# 束線の分岐: ケーブルの片側を1本線、もう片側を芯線ごとに描く

日付: 2026-10-25 · 状態: 利用者が未決事項を決定済み、設計書のレビュー待ち · English: [2026-10-25-cable-breakout-design.md](2026-10-25-cable-breakout-design.md)

## 目的

1本のケーブルを、**途中までは1本の線、そこから先は芯線ごとの配線**として描けるようにする。そのうえで、どの芯も端から端まで自分の接続を保つ。ネットリスト・From-To電線リスト・部品表・ケーブル一覧・ERC・電気検証のどれもが、芯1本を1本の導体として扱う。

AOGUの配線図で今これが要る:

| ケーブル | 1本線で描く側 | 芯線ごとに描く側 |
|---|---|---|
| LTEハーネス 45/46 | USB Type-A プラグ/ソケット | 基板の JST XH 4P: VBUS / D− / D+ / GND の4本 |
| デバッグケーブル 58 | 3.5 mm TRS (AUDIO) | Raspberry Pi ヘッダのピン 8 / 10 / 6 へのデュポン3本 |
| アンプ電源 54 | USB | アンプのねじ端子: 5V / GND の2本 |

もう1つの小さな使い方: 多ピンのコネクタ同士を**全長1本線**で結ぶケーブル (例: 3.5 mm AUX ケーブルの L / R / GND)。これも芯ごとの接続を保つ。

できあがりの目安: LTEハーネスを「基板側4本の配線が1本の線にまとまってUSBプラグへ行く」形で描ける。そのとき `get_netlist` は別々の4ネット (`J45:1–USB1:1`、`J45:2–USB1:2`…) を返し、ERCは短絡・未接続ピン・宙ぶらりんの配線を1件も出さず、電線リストは芯ごとに1行になる。AIエージェントはこれをMCPの1回の呼び出しで描ける。

## 今の困りごと

ネットリスト (`madake-core/src/netlist.rs` の `extract_netlist`) は位置で繋ぐ:

- 配線同士は**端点**が重なったところ (かジャンクションの点) だけで繋がる
- シンボルのピンやネットラベルは、配線の**どこか1点**に乗っていれば (`CONNECT_EPS` = 0.01 mm 以内) 繋がる。端点でなくてもよい

このため、LTEハーネスのUSB側を1本線で描こうとすると、正しく描ける場所が無い:

- `connector_4p` のピンの列 (4本とも x = +7.5 mm、5 mm 間隔) に沿って線を引くと4本のピン全部に触れ、ネットリストは **VBUS・D−・D+・GND を1つのネットに短絡**させる
- 基板側の4本の配線を1本線の始点で終わらせると、4本の端点が重なるので、これも1つのネットになる
- AOGUの図面では、偽の「分岐」ブロック (入力1ピン・出力Nピン) で逃げている。ERCは黙るが、ネットリストはブロックで止まり、`J45:2` (D−) から `USB1:2` へのつながりが無くなる。電線リストも検証も、今後のハーネス検査も、ケーブルの中を芯ごとに辿れない

この短絡をERCでも見つけられない。「1本のケーブルの芯2本が同じネットにある」を調べる検査が無いため。

## 今の作り

- **`Entity::Cable`** (`model.rs`、形式15) は EPLAN 流の*ケーブル定義*。ケーブルに入る配線を斜めに横切る**定義線** (`points`、ちょうど2点) で表し、`add_cable` が横切った配線を順に芯へ割り当てる (`CableCore { core, color, wire }`)。参照記号 (W1…)・型番・芯数・線径・シールド・長さを持ち、ケーブル一覧 (`cable.rs` の `cable_list_rows`)・部品表のケーブル行 (`cable_bom_rows`)・ERC 1種 (`erc.cable_core_overflow`) に出てくる。**ネットリストからは見えない** (`extract_netlist` で `Entity::Cable(_) => {}`)。芯は全部、それぞれ1本の `Wire` として描かれている
- **`Entity::Harness`** は破線の囲みを描いて、中の配線に名前を付けるだけ
- **ネットリスト**はシート単位。シートを跨ぐ統合は `xref::extract_netlist_project` がネットラベルで行う。`extract_netlist` の呼び出し元は約20か所 (ERC・SPICE/シミュレーション・KiCadネットリスト出力・線番・クロスリファレンス・PLC・MCPの `get_netlist`・Link API)。ネットリストで直せば全部に効く
- **ネットには配線が要る**。`extract_netlist` は `Wire` を1本以上含むまとまりしかネットにしない。配線の無いピン同士の接続は今は存在しない
- **`erc.unconnected_pin`** はネットリストを見る。**`erc.dangling_wire`** は配線の端点を位置で調べる別の検査
- **電線リスト** (`reports.rs` の `wire_list_rows`) は `Wire` 1本につき1行。`wire_from_to` が両端をピンに解決するか、ネットラベル越しに辿る (G18)
- **部品表の電線集約** (`wire_rollup_rows`) は全 `Wire` の長さを電線品番ごとに足す。ケーブルの芯になっている配線も足すので、ケーブルの芯はケーブル行と電線行で2回数えられている
- **MCP**: `connect_pins` はピン同士の配線を1本でも複数 (`connections`) でも、undo 1回ぶんで引く。`place_mate` はプラグ/ソケットの組を置く。`execute_commands` は生の `Command` (`add_cable` を含む) を流す。ピン位置と経路は `pin_wiring.rs` (`resolve_pin`・`plan_connection`・`route`) が求める
- **ファイル形式**は16。`io::migrate` は版番号を上げるだけ。`load_project` は**アプリより新しいファイルを拒まない**し、serde は既存の構造体の知らないフィールドを無視する。つまり `Cable` にフィールドを足すと、古いビルドは**黙って捨て**、次に保存したときに消える
- `Entity::refs` / `remap_refs` がシート内の参照 (今は引き出し線の対象・ケーブル芯の配線・銘板・寸法線) を列挙する。シート複製 (整えバリアント) とマクロがこれに頼っている

## 他のツールのやり方

確かめられたことだけを書き、それ以外は印を付ける。

- **EPLAN** は*ケーブル*と*その描き方*を分けている。ケーブルは接続の上に引くケーブル定義線か接続定義点で定義し、表示形式 (単線/複線) はページの種類から決まる ([ケーブル定義](https://www.eplan.help/en-us/infoportal/content/Plattform/2.9/Content/htm/cablegui_k_arbeitsweise.htm))。単線ページでは導体の本数を接続定義点のプロパティで持ち、図には「ふつうはスラッシュで」示され、`3+PE` のような値も書ける。複線と単線の切り替えは**バンドル接続点**が受け持ち、接続は「1本の太い接続線からなるバンドルへ送り込まれ」、行き先の手前で再び分かれる ([ケーブルの特記事項](https://www.eplan.help/en-us/infoportal/content/Plattform/2026/Content/htm/singlepole_k_besonderheitenkabel.htm))。バンドル内の各接続は**バンドル接続点の名称**で見分け、名称はバンドルの入口と出口の接続点に対で入る。名称はケーブルの芯番号や芯色で上書きできる ([単線表示のバンドル](https://www.eplan.help/en-us/infoportal/content/Plattform/2026/Content/htm/singlepole_k_straenge_in_einpoligerdarstellung.htm))。つまり EPLAN では、1本線を通る芯の同一性は**名称の一致**で決まり、位置では決まらない。未確認: バンドルを最初に描いたとき EPLAN が名称を自動でどう振るか
- **KiCad** のバス: ベクタバス `D[0..7]`、グループバス `USB1{DP DM}` (メンバはネット `USB1.DP`・`USB1.DM` になる)、バスエイリアス。バスエントリは「見た目だけで、論理的な接続には要らない」。接続は「ピンに繋がった配線に置いたラベルで決まる」。ピンはバスへ直接は繋げない ([KiCad 8 回路図エディタ マニュアル](https://docs.kicad.org/8.0/en/eeschema/eeschema.html))。芯の同一性は**ネットラベル名**で決まる
- **ハーネス設計ツール** (Zuken E3.cable、Siemens Capital、EPLAN Harness proD): ハーネス図で束とケーブル芯を扱うことは知られているが、この設計書のためには確かめていない。根拠には使わない

共通する考え方: 1本線は**名前付きのメンバを並べて運ぶもの**で、各メンバは**名前か割当てで明示的に**配線やピンへ結ばれる。触れているかどうかでは決めない。MadakeCAD も同じにする。芯→ピン・芯→配線の割当てを明示的に持たせ、その持ち主はケーブルにする。

## 案

### A. 新しいエンティティ `Bundle` (EPLAN のバンドル)

新しいエンティティ: メンバの並びと2つの端を持つ折れ線。端は「分岐 (メンバが配線として続く)」か「部品に着く (メンバがピンへ行く)」。1本のバンドルに、1本のケーブルの芯も、複数のケーブルの芯も、ただの配線も通せる。

- 良い点: EPLAN にいちばん近い。バンドルは作図だけで、ケーブルは部品のまま。新しい `Entity` の種類なので、**古いビルドはファイルを開くのを拒む** (知らないタグ)。黙ってデータが消えることは無い
- 悪い点: 1本の実物のケーブルを2つのエンティティで表す (部品表のケーブル行には `Cable`、作図には `Bundle`)。利用者もエージェントも両者を合わせ続けなければならない。コード中に15ほどある `match Entity` の全部に1種類増える。複数ケーブルの芯を1本線に通す使い方は AOGU のどの例にも無い

### B. `Cable` に1本線の区間と芯ごとの端の割当てを足す (推す案)

今のケーブルに、省略できる**区間** (1本線) を持たせ、各芯に明示的な**端**を持たせる。端は「部品のピン」か「その芯自身の配線 (分岐)」。ネットリストは各芯の両端を明示的に結ぶ。

- 良い点: 実物のケーブル1本に対してモデルも1つ。参照記号・型番・芯数・線径・シールド・長さはもうあって、ケーブル一覧と部品表にもう流れている。EPLAN の「同じケーブルを単線で表す」と合う。エージェントが作るものは1つで済む
- 悪い点: 古いビルドは新しいフィールドを黙って捨てる (「ファイル形式」の項)。1本の区間に2本のケーブルの芯を通せない (今は要らない。要るようになれば後から A を足せる)

### C. ネットリスト側の「バス配線」(KiCad のバス)

`Wire` にメンバの並びを持たせ、それに触れた配線はネットラベルでメンバを選ぶ。

- 良い点: モデルの変更が最も小さい
- 悪い点: 芯の配線すべてにラベルが要る。ピンをバスに乗せられないので、USB側 (1本線がそのままプラグへ入る) が描けない。ラベルを間違える・付け忘れると、ネットが黙って割れるか混ざる。ケーブル部品・部品表・ケーブル一覧と結び付かない。エージェントが正しく描くのが難しい

### 推す案

**B を推す**。本当の困りごと (1本線を通しての芯ごとの接続) を明示的な割当てで解き、実物のケーブル1本にモデル1つを保ち、今あるケーブル一覧・部品表の行・プロパティ画面をそのまま使える。1本線に複数のケーブルを通す必要が出てきたら、そのとき A を足せばよい。

## 設計 (案B)

### 1. データモデル (`model.rs`、形式17)

メモリ上は `Cable` の構造体1つ。ファイルには、`run` を持つケーブルをエンティティの種類 `run_cable` で、持たないものを今までどおり `cable` で書く (6章: 古いビルドには区間ケーブルを捨てさせず、読み込みに失敗させる)。

```rust
pub struct Cable {
    // ... 既存のフィールドはそのまま: id, reference, part_no, core_count, sq,
    //     points (定義線), cores, shield, length_m
    /// 1本線の区間 (描かれる「1本の線」)。用紙座標mm。空 = 従来の定義線ケーブル。
    /// 配線と同じ直交の折れ線。
    #[serde(default, skip_serializing_if = "Vec::is_empty")]
    pub run: Vec<Point>,
}

pub struct CableCore {
    pub core: String,          // 呼び名: "1", "VBUS", "D-", "L" …
    pub color: String,
    pub wire: Option<EntityId>, // 既存: 定義線が横切った配線
    /// 区間の始点 (run[0]) 側・終点側で、この芯がどこへ出るか。
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub end_a: Option<CoreEnd>,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub end_b: Option<CoreEnd>,
}

#[serde(tag = "kind", rename_all = "snake_case")]
pub enum CoreEnd {
    /// 区間が部品に着き、この芯はこのピンになる
    /// (ピン番号。同じ番号の接続点が複数あるときは `index` で何番目かを選ぶ。"TB1.1#2" と同じ)。
    Pin { part: EntityId, pin: String, #[serde(default)] index: Option<u32> },
    /// 分岐: 芯はこの配線として続く。配線の端点のうち区間の端に近い方が分岐側の端で、
    /// 遠い方の端はいつもどおり結線する。
    Wire { wire: EntityId },
}
```

決まり (今のケーブルの検証と同じく `Engine::execute` が調べる):

- ケーブルは**定義線ケーブル** (`points` が2点・`run` は空・`end_a`/`end_b` 無し) か、**区間ケーブル** (`run` が2点以上・`points` は空でよい) のどちらか。今の「ちょうど2点」の検査は「2点、または区間がある」に変わる
- 区間ケーブルでは、どの芯も両端を持つ。`Pin` はシート上のシンボルとそのピンを、`Wire` はシート上の配線を指す。1本の配線・1本のピンを使える芯は1本まで
- `Entity::refs` / `remap_refs` に `CoreEnd` の参照先を入れる。シート複製・整えバリアント・マクロで割当てが保たれる
- 芯が使っている部品や配線を消すと、端は何も指さなくなり、ERC が報告する (下記)。今、芯の配線を消したときと同じ扱い

区間の点はケーブルと一緒に動く (`translate`)。区間は描画も当たり判定もされるが、**決して `Wire` ではない**。だからピン・ラベル・配線の端が位置で区間に繋がることは無い。

### 2. ネットリストの決まり (`netlist.rs`)

区間ケーブルの芯1本ごとにノードを1つ足し、

- 芯ノード ↔ `Pin { part, pin }` の接続点すべて (そのピン番号の全部、または `index` 番目だけ)
- 芯ノード ↔ `Wire { wire }` の配線
- 区間には位置では何も繋がらない

と結ぶ。**配線か芯を1つ以上**含むまとまりをネットにする (今は配線1本以上)。これでコネクタ同士の1本線ケーブル (AUX の L / R / GND) は、`Wire` が1本も無くても3つのネットになる。

`Net` にフィールド `cable_cores: Vec<NetCableCore { cable_id, reference, core }>` を足す (serde 既定値付き。IPC と MCP の JSON は増えるだけ)。ネット名の決め方は変えない (ラベル → 線番 → `N001…`)。芯だけのネットは配線のあるネットの後ろにケーブルid順で並べるので、今あるネット名はずれない。

ネットリストの利用者は全員 `extract_netlist` を通るので、ERC の `erc.unconnected_pin`・SPICE・クロスリファレンス・KiCad ネットリスト出力・`get_netlist` は手を入れなくても芯を見る。

### 3. ERC (`cable.rs` の `check_cables`、`verify.rs`)

| コード | 重さ | 出るとき |
|---|---|---|
| `erc.cable_cores_shorted` (新) | エラー | 1本のケーブルの芯2本が同じネットにある。定義線ケーブル (芯の配線) にも効く。今の偽の分岐ブロックが隠している短絡はこれで見つかる |
| `erc.cable_core_unassigned` (新) | エラー | 区間ケーブルの芯に `end_a`/`end_b` が無い、または消えた部品・無いピン・消えた配線を指している |
| `erc.cable_run_end_detached` (新) | 警告 | `Pin` の芯を持つ区間の端が部品の上やすぐそばに無い (部品の外形から 2.5 mm より遠い)。線がどこへ行くか図から読めない |
| `erc.cable_core_overflow` (既存) | エラー | 区間ケーブルの芯も数える |
| `erc.dangling_wire` (変更) | — | 芯の分岐側の端になっている配線の端点は「繋がっている」と数える |

### 4. 電線リスト・ケーブル一覧・部品表 (`reports.rs`、`cable.rs`)

- **電線リスト (From-To)**: 区間ケーブルは芯1本につき端から端まで1行。From/To は両端を辿る。`Pin` の端は `USB1:2`、`Wire` の端はその配線の遠い方の端を今と同じに解決する (ピンかネットラベル、G18)。線色は芯、線径はケーブル、ハーネス列はケーブルの参照記号。分岐の配線は芯の一部なので、別の行にはしない。末尾に新しい列 `ケーブル芯` (`W45/D-`) を足す。末尾に足すので、列の位置で読むスクリプトは壊れない。
- **ケーブル一覧**: From/To の機器は `Pin` の端からも取る。使用芯 = 両端のある芯
- **部品表**: ケーブル行は変えない (型番ごと)。区間ケーブルの分岐の配線は電線集約に**足さない** (ケーブルの芯なので)。定義線ケーブルにも同じ決まりを当てる: どれかのケーブルの芯になっている `Wire` は電線集約に足さない (今の二重計上を直す)

### 5. 描画 (`svg.rs`、`src/canvas/cable.ts`)

- 区間は配線より太い線 (配線 0.35 mm に対し 0.7 mm) で描き、中ほどに単線図のふつうの印、短い斜線と芯数 (`/4`) を付ける。EPLAN が接続数を示すのと同じ。ケーブルの注記 (`W45  4C×0.2sq  0.3m`) は定義線の代わりに区間の横に置き、シールドの楕円は斜線の印を囲む
- **部品に着く端** (`Pin` の芯): 芯が着くピンの先を横切る短い棒を描き、区間の端と結ぶ。それらのピンが全部この線から来ていることが一目で分かる (棒は作図だけ)
- **分岐の端** (`Wire` の芯): 区間の端から各芯の配線の分岐側の端へ短い扇形の線を描き、各配線の端に芯の呼び名を小さく (シートの注記文字高で) 添える。分岐側の端どうしは別の点でなければならない。経路づくりは 2.5 mm グリッド上に並べる
- 作図領域 (`cable.ts`): SVG と同じ形 (同じ決まりを、両側のテストでそろえ続ける)、区間の当たり判定、ケーブルツールに**1本線区間**のモードを足す: 1つ目の端 (部品、分岐なら点) をクリックし、経路を引き、2つ目の端をクリックする。ダイアログで芯の表 (呼び名・線色・端A・端B) を埋める。既定はピン順。プロパティ画面の芯の表に「端A」「端B」の列を足す
- DXF と KiCad 回路図の書き出しは今どおりケーブルを描かない。KiCad の**ネットリスト**の書き出しは、何もしなくても芯ごとの正しいネットになる

### 6. ファイル形式と互換性

- `FORMAT_VERSION` を17にする。古いファイルはそのまま開く (新しいフィールドはどれも空が既定)。区間ケーブルの無いファイルは、版番号以外1バイトも変わらずに保存される
- `load_project` に「**アプリより新しい** `format_version` のファイルは分かりやすい理由を添えて拒む」を足す。この先の形式変更すべてを守る。区間を持つケーブルは新しいエンティティの種類 `run_cable` (構造は `cable` と同じ) で保存する。この変更より前のビルドは種類を知らないので、区間を黙って捨てずにファイルの読み込みに失敗する。区間の無いケーブルは `cable` のまま
- AOGU の図面の偽の分岐ブロックの置き換え: `connect_cable` ができたらそれで描き直す。補助ツール `replace_breakout_block` は作らない

### 7. エージェント向けの MCP API

新しいツールを1つ。`connect_pins` と同じ作り (ピン名で指定し座標は要らない、全部を undo 1回ぶんで行う、どこか1つでも駄目なら何も描かない):

```jsonc
connect_cable({
  "sheet_id": "…",                         // 省略時は先頭シート
  "reference": "W45",                      // 省略時は次のW番号
  "part_no": "", "sq": 0.2, "length_m": 0.3, "shield": null,
  "cores": ["VBUS", "D-", "D+", "GND"],    // または [{ "core": "VBUS", "color": "red" }, …]
  "a": { "pins": ["J45.1", "J45.2", "J45.3", "J45.4"], "style": "multi",
         "breakout_at": { "x": 120, "y": 80 } },          // 省略時は自動
  "b": { "part": "USB1", "style": "single" },             // pins 省略時はその部品のピンを順に
  "via": [{ "x": 160, "y": 80 }]                          // 区間の経由点 (省略可)
})
// → { "cable_id": "…", "run": [点の列], "cores": [
//      { "core": "VBUS", "a": "J45.1", "b": "USB1.1", "wire_id": "…" }, … ],
//     "revision": 42 }
```

- `style: "multi"` は、各ピンから分岐側の端まで芯ごとに1本ずつ配線を引き (`connect_pins` と同じ経路づくり。別のピンの上を通るなら断る)、`Wire` の端にする。`"single"` は区間を部品に着け、`Pin` の端にする。両端とも `"multi"`、両端とも `"single"` もできる (AUX の例: `a: { "part": "J1", "style": "single" }, b: { "part": "J2", "style": "single" }`)
- `pins` は `"J45.1"` の文字列でも、`part` とピンの並びでも書ける。数は芯数と同じでなければならず、違えば断り、どちらの端が違うかを知らせる
- `cables: [ … ]` で複数のケーブルを1回で描く (`connections` と同じ)
- 自分で座標を組み立てるエージェント向けに、`execute_commands` の `add_entity` で区間ケーブルを足しても同じ検証が効く
- `get_netlist` は各ネットに `cable_cores` を載せ、`get_project` は新しいフィールドを返す。スキル `drawing-madakecad-wiring` と `docs/10-automation-api.md` に「1本線のケーブル」の短い節を足す

## テスト

Rust のテストは `#[test]` の上に2行のドキュメント (英語、次に日本語) を書く。Vitest のテストは `it(...)` の直前に `// ja:` の行を書く。`python3 scripts/gen_spec.py --check` が通ること (同じ PR で `docs/13-specification*.md` を作り直す)。

- `netlist.rs`: LTEハーネス (4本の配線 → 区間 → `connector_4p`) が別々の4ネットになり、各ネットに基板のピン1本とプラグのピン1本がある。コネクタのピン列に沿って置いた区間は何も繋がない。コネクタ同士の区間は配線無しで芯ごとに1ネットになる。`index` で貫通端子の片側を選べる
- `cable.rs` / `verify.rs`: 芯2本が同じネットなら `erc.cable_cores_shorted` (区間ケーブルでも定義線ケーブルでも)。端の無い芯・消えた配線を指す芯は `erc.cable_core_unassigned`。部品から遠い区間の端は `erc.cable_run_end_detached`。分岐側の配線の端は宙ぶらりんにならない。芯からだけ給電されるピンは未接続にならない
- `command.rs`: 形の崩れた区間ケーブル (2本の芯が同じ配線を使う・同じピンを2回使う・芯の呼び名が重なる・端の種類が違う) は断る。行き先が無いだけなら受け入れて ERC が報告する。行き先を消した後でも undo やプロパティの編集が効くように。undo 1回でケーブルとその配線が消える。シートを複製しても `remap_refs` が芯の端を保つ
- `reports.rs`: From-To は芯ごとに端から端まで1行で、`ケーブル芯` 列がある。分岐の配線は部品表の電線集約に入らない
- `io.rs`: 区間ケーブルが保存と読み込みで変わらない。v16 のファイルが開けてケーブルが残る。アプリより新しいファイルは断る
- `svg.rs`: 区間・芯数付きの斜線の印・部品側の棒・分岐の扇形が描かれる
- MCP (`madake-mcp`): `connect_cable` が LTE ハーネスを1回の呼び出し・undo 1回で描く。ピンの数が違えば断り、何も描かない。`cables` で複数描ける
- Vitest (`src/canvas/cable.test.ts`): 区間の注記と斜線の印が Rust の決まりと同じ。区間の近くのクリックで選べる。区間ツールが2回のクリックを1つのコマンドにする。芯の表の既定がピン順

## 未決事項の決定 (2026-10-25)

1. 進め方: 案B (`Cable` を広げる)。
2. 電線リスト: 芯ごとに端から端まで1行。分岐の配線はその行にまとめ、末尾に `ケーブル芯` の列を足す。
