# Wire Management

[日本語](05-wire-management.ja.md)

Industrial wiring diagrams live and die by wire data: color, gauge, length, and part numbers. MadakeCAD treats these as first-class wire attributes that flow into reports and verification.

## Available

- **Per-wire attributes**: color (named palette incl. Japanese conventions), gauge in sq (mm²), optional length (m), wire part number, optional net name
- **Wire annotation on the sheet**: every wire prints its own `0.75sq white 0.4m` note, built from the gauge, colour and cut length stored on it. It goes on the wire's longest segment, on the **opposite side from the wire number** (below a horizontal run, right of a vertical one), and a missing attribute is simply left out — a wire with none gets no note. A black wire with no gauge and no length also gets no note: black is the default colour, and "黒" on every line would only clutter the sheet. A black wire with a gauge or a length still names its colour. Colour names are matched ignoring capitals and surrounding space: a colour the drawing knows prints its display name (`Red` and `red` both print 赤), and one it does not know prints as typed but lower-cased (`Turquoise` → `turquoise`, `#FF0000` → `#ff0000`). The legend block and the wire-part lookup use that same name, so the three can never disagree. It has its own view class on screen and is **always** written to SVG and PDF, because on an industrial wiring diagram this is the information the wire is made from
- **Wire part master**: color + gauge → wire part number lookup, stored in the global parts database (with per-meter price and procurement URL); the project file keeps its own snapshot so drawings stay self-contained
- **Wire part number resolution**: a wire's own part number always wins; when it is empty the wire's **colour + gauge** is looked up in the project's wire-part table (the first matching row wins, and an unmatched combination simply stays blank), and the wire list and the from–to report follow. Matching ignores case and surrounding space and treats the English and Japanese names of a colour as the same colour, so a table written `青` resolves a wire drawn `blue`. The table can be imported from CSV (`colour, gauge sq, part number[, note]`, header optional) as **one undoable command**; `POST /api/v1/project/wire-parts/csv` and the `import_wire_parts_csv` IPC call do the same. The properties panel shows the resolved number as *Part number (automatic)*
- **Wire part-number legend block**: an auto-drawn table (Schematic tab → Wiring group → *Wire legend*) with one row per distinct colour+gauge+part-number combination among a sheet's wires — colour, gauge, part number (resolved the same way as above) and the summed length of that combination on that sheet. A colour is grouped and printed under the name the wire annotation uses on the same sheet, so wires recorded as `red` and as `赤` are one row, not two. Rows are sorted by colour, then gauge, then part number, and the summed length is printed in metres to two decimals, the same format the BOM's wire roll-up uses; a sheet with no wires still draws the header. It holds no content of its own — see [Schematic editor](03-schematic-editor.md) for the full entity description
- **BOM wire roll-up**: the bill of materials adds, after the component rows, one row per wire part number with the project-wide total length, and one `(unassigned)` row for wires whose part number cannot be resolved — see [Standards output](04-standards-output.md)
- **Electrical semantics**: wire gauge and length feed ampacity and voltage-drop verification; terminal blocks provide feed-through connectivity in the netlist
- **Wire numbers**: net-scoped numbers stored on every wire of the net. Automatic numbering (Schematic tab → Wiring group → *Wire numbers*) runs in two modes — *top-up*, which keeps existing numbers and net labels and only fills in unnumbered nets, and *renumber*, which reassigns every automatically generated number; manually typed names are always kept. Numbers are issued top-to-bottom, then left-to-right, are unique across the whole project when no sheet is given, and never collide with a net label. They are drawn on the wire (above a horizontal run, left of a vertical one) and can be edited one net at a time in the properties panel. Same command from the CLI: `madake renumber [--sheet <ID>] [--mode append|renumber] [--start N]`
- **Multi-core cables** (ribbon Schematic → Wiring → *Cable*): drag a **definition line** across the wires that run in one cable; the wires it crosses become cores 1, 2, 3… in order from the start of the line, each core taking the wire's colour, and the core count defaults to the number of wires crossed. The cable is drawn as the slanted line with the label `W1  SAMPLE-CBL  4C×1.25sq  12.5m` and, with a shield, an ellipse around the line. In Properties set the designator, part number, core count, gauge, shield (and grounding) and length; the core table lists the assigned cores and the spare ones. More assigned wires than cores is an ERC error (`erc.cable_core_overflow`). A cable is a part with a part number and core assignments, unlike a harness boundary, which only names a bundle. Placing a cable is one `add_cable` command (undo restores it); the `.mdkproj` format is 15. DXF and KiCad exports do not carry cables
- **Single-line cables (cable breakout)**: a cable can be drawn as **one line** on one end, or along its whole length, while every core keeps its own connection. Each core says where it goes at each end of the line: a **pin** of the part the line lands on (drawn as a bar across those pins), or the **breakout wire** it continues as (drawn as a short fan from the end of the line, with the core name). The netlist joins each core only through these assignments, never because the line touches something, so a line over a connector's pin column shorts nothing, and a cable drawn as one line between two connectors gets one net per core even without wires. The line is drawn thicker than a wire, with a slash and the core count. ERC adds `erc.cable_cores_shorted` (two cores of one cable in the same net, also for definition-line cables), `erc.cable_core_unassigned` (a core whose pin or wire is gone) and `erc.cable_run_end_detached` (a line end away from its part); breakout wire ends are not dangling. The From-To list has one row per core, end to end; wires that are cores of any cable are not counted again as loose wire in the BOM. `length_m` is the whole cable. Draw one with the MCP tool `connect_cable` (cores map to pins in pin order). A cable with a line is saved as the entity kind `run_cable` (`.mdkproj` format 17), so older apps refuse such files, and MadakeCAD refuses a file newer than itself
- **Port pins (multi-contact pins)**: a block pin can carry several named conductors, its **contacts** (for example a USB-A socket `U3` with `VBUS, D-, D+, GND`). It is drawn as one pin, and the netlist splits every net that holds a port into one net per contact, named `<net>.<contact>` (`USB_MIC.VBUS`, `N003.D+`). One wire between two ports connects same-named contacts. A plain pin joins the contact with its pin name (`GND`). A mate half (plug or socket) passes every contact through, but plug and socket are still not joined to each other. A label `<label>.<contact>` on another wire taps one contact, also across sheets. Wire numbers, the wire list and the BOM still count the drawn wire once. ERC adds `erc.port_to_plain_pin` (a plain pin on a port whose name matches no contact), `erc.port_contact_unmatched` (a contact on only one of the joined ports) and `erc.port_label_unsplit` (a port label used on another sheet without a port). A run cable can end on one port pin (`connect_cable` with `pins: ["39.U3"]`). Edit contacts in the block pin table (comma separated; 2 to 32 per pin, trimmed, unique within the pin). A pin's `connector` picture (see [Schematic editor](03-schematic-editor.md)) is independent of its contacts: a USB socket pin normally has both. A file with port pins or connectors is `.mdkproj` format 19; blocks with contacts or connectors are saved as the entity kind `port_block`, so older apps refuse the file
- **Harness boundaries**: a dashed rectangle with a name (`W1`, `W2` …) and a note, for a group of wires made and bought as one bundle. **An enclosure or case outline is drawn with a graphics rectangle instead** (Schematic tab → Graphics group): a harness around a case would make every conductor merely sitting inside it inherit the case name in the wire list and the terminal chart. Membership is geometric — a wire belongs to the harness that encloses all of its points, and the innermost enclosure wins for nested boundaries. Drawn with the harness tool (Schematic tab → Wiring group → *Harness*, drag a rectangle), edited in the properties panel, which also shows how many wires are enclosed
- **From–to wire list report** (CSV) with sheet, from, to, mate, remark, wire number, color, gauge, length, part number, harness, cable core (`W45/D-` for a wire that is a cable core; a single-line cable gives one row per core). From and To are the two ends of the wire: a pin is written `reference:pin` (`K1:A1`, `TB1:3`), a net label as its name, an end that touches nothing stays empty; of the two ends the alphabetically smaller one is From, and an unconnected end is always To. **An end that lands on a net label is followed through the net** (excluding this wire's own other end, if it is a pin): when the net has exactly one other pin, the label is replaced with that device's `reference:pin`; otherwise the label stays and the remark column says why: `multi` when the net has several other pins and no single one can be picked, `none` when the net holds no device pin at all so there is nothing to reach (a row where both apply is marked `multi`). Rows are **one per wire**, so two wires that resolve to the same pair of devices — for example the two stubs on either side of a pair of same-named net labels — are two rows that read alike; they are different wires, each with its own colour, gauge and length. **Mate column and net-label resolution are new and are inserted right after To, so the CSV is not compatible with the previous 9-column export** (12 columns now, with the cable-core column appended last) — a script that reads the wire list CSV by column position must be updated, the same way the terminal chart's Lv column broke its own compatibility
- **Mating connector pairs** (G14): `attrs["mates_with"] = "<designator>"` on a connector instance (the `connector_*` family: dynamic `connector_{n}p` and the static `connector_plug`/`connector_socket` — terminal blocks are not connectors for this purpose) declares one side of a mated pair; declaring it on both sides links the pair fully. ERC (project-wide, since a mate can point at another sheet): a pole-count mismatch between the two connectors is a Warning (`erc.mate_pole_mismatch`), a declaration the other side does not reciprocate is an Info (`erc.mate_one_sided`), and a self-reference or an unknown designator is a Warning (`erc.mate_unknown`). The wire list and from–to report's **mate** column shows the declared mate of whichever end resolves to a device, From side first, so the column reads the same however the wire was drawn. On the drawing, a short dashed line is drawn automatically between the two instances' nearest outline points **only** when both are on the same sheet and within 50 mm of each other (50 mm exactly still counts) — otherwise nothing is drawn and the reports alone carry the pair. On screen the line belongs to the *symbols* view class, since it is drawn between two symbols: hide the symbols and the line goes with them. As with every view class, SVG and PDF export always draw it. Edited from the properties panel (a "Mate" field appears for connector instances) or through any command path. No gender field on the parametric connector family yet
- **Terminal chart**: one table per terminal strip, one row per terminal, in terminal-number order — terminal, **level (Lv)**, internal target, external target, wire number, wire (color, gauge, part number), harness, jumpers. The Lv column carries the level letter of a multi-level terminal block's terminal (e.g. `1a`) and stays blank for an ordinary single-level block. A terminal nothing is wired to is listed as a *spare*. Inside/outside follows panel practice: **a connection on the left-hand pin is the internal (in-panel) side, on the right-hand pin the external side**, judged after rotation. Available as CSV and as a framed drawing sheet. **The Lv column is new and is inserted right after the terminal column, so the CSV is not compatible with the previous 6-column export** (7 columns now, 8 for the project-wide chart) — a script that reads the chart CSV by column position must be updated
- **Terminal connection diagram**: the graphical EPLAN-style form of the same data — the terminal strip runs down the page **staggered, one box per row**, with **the external side on the left and the internal side on the right**, leader lines to each target, wires of one harness gathered under a named bracket, spare terminals shaded, jumpers drawn as a bar along the strip. For a multi-level terminal block the strip is split into one column per level, headed by the level letter, and each box carries the full level-letter terminal number (`1a`, `1b`, …), so the levels are drawn as the separate columns of terminals they are. **Saddle jumpers use a lane per level**: a jumper between the two levels of one pole always links physically adjacent rows (a pole's levels are never split apart, whatever the row order), so it uses the same close lane a single-level block would; a jumper between neighbouring poles of one level skips over the other levels' rows in between (the staggered layout draws one row per terminal, not one row per pole), so it is routed through a lane of its own, placed beyond every row's leader line — never through the band where a skipped row's own leader line runs. One terminal block per page (15 terminals per page, split automatically). PDF only
- **Terminal strip editor** (Reports tab → Terminal blocks group → *Terminal editor*): a grid of the chart rows for the selected terminal block (with the chart's **Lv** column, shown only when the block has more than one level), a toolbar, and footer buttons that generate the chart or the connection diagram. Every edit here is one `update_entity` command on the terminal block, so Cmd+Z takes it back and the editor, the chart, the connection diagram and the schematic symbol all follow
  - **Saddle jumpers** between neighbouring terminals, stored as `attrs["jumpers"] = "1-2,3-4"` (each pair in terminal order). On a multi-level block the pair carries the level letter (`1a-1b` across the levels of one pole, `1a-2a` along one level); a plain numeric pair, or a terminal the block does not have, is flagged by the terminal check. On the symbol the jumper is drawn as a short bar filling the gap between the two terminals' round marks, at more than twice the weight of an ordinary symbol line — the way a saddle jumper sits on a real block
  - **Row order** (sort dropdown, stored as `attrs["row_order"]`; an unset or unknown word means number order): number (default), alphanumeric (terminal numbers compared as text, so `10` sorts before `2`), page (by where the pole's wiring first appears in reading order — top to bottom, then left to right — unwired poles last), external cable (poles grouped by their external harness, in the order that harness name first appears) and jumper (jumpered poles first). **Page order is compared by frame zone and only over the terminal block's own sheet**, so poles whose wiring lands in the same zone keep their number order. A multi-level terminal's levels stay next to each other whichever order is chosen, and the chart CSV, its framed drawing sheet and the connection diagram all come out in the editor's order
  - **Auto-numbering** (toolbar *Renumber* popover: start number, step, prefix, a preview of the resulting labels, Apply/Cancel), stored as `attrs["terminal_numbers"]` — a comma-separated list of labels in pin order (the same order as the block's default numbers), unset meaning the symbol's own defaults (`1`, `2`, … or, on a multi-level block, `1a`, `1b`, …). Renumbering keeps each pole's level letters and only changes the pole number, so every level of one pole still shares one new number. A count that does not match the pin count, a duplicate label or an empty item is refused without touching the drawing. **The same command rewrites `attrs["jumpers"]` and any `attrs["pin_groups"]` ranges to the new labels**, so a jumper or a pin-group range still names the terminals it actually connects; jumper adjacency is decided from the block's raw pin layout, not from the arithmetic difference between the displayed labels, so a step greater than one does not break an existing jumper between physically neighbouring poles. The overridden labels show up everywhere a terminal number is drawn or listed — the editor grid, the chart CSV, the framed chart sheet, the connection diagram, the terminal check, and the schematic symbol itself (SVG/PDF export and the on-screen canvas draw the same substituted label, from one raw-pin-number-to-label table). Direct entry (`SetTerminalNumbers`, `numbers: null` to return to the defaults) is the undo inverse of a renumbering, one Cmd+Z step. A label must not be blank or contain a comma (the separator of the stored list), and two labels that differ only in their surrounding spaces count as a duplicate; a jumper or pin-group item the editor cannot read, or one naming a terminal the block does not have, is carried through a renumbering unchanged, so the design check keeps pointing at it and one undo restores the attribute byte for byte — **except in the documented corner case where the old and new label sets overlap and the unreadable item names a label that does not exist under the old numbering but happens to match one of the new labels**: the reverse rewrite can then recognise and rewrite a token the forward rewrite left untouched, so undo is not guaranteed byte-identical there. The netlist and the From-To list keep using the electrical pin identity (the symbol definition's pin numbers); the renumbered display labels appear in the chart, the connection diagram and the drawing
  - **Go to drawing** (toolbar button, or a double-click on a row) closes the editor and switches to the terminal block's sheet, selecting and zooming to it; reopening the editor comes back to the same block and row selection
  - **Level count (1–3), added and removed in place** (toolbar *Multi-level* popover: a level stepper, a preview of the new symbol id, the new terminal numbers and the jumpers that follow, Apply/Cancel), one `SetTerminalLevels` command. It rewrites the block's `symbol_id` between `terminal_block_{n}p` and `terminal_block_{n}p_{levels}l` and carries `attrs["terminal_numbers"]`, `attrs["jumpers"]`, `attrs["pin_groups"]` and `attrs["accessories"]` forward onto the lettered labels, so a levelless jumper `1-2` becomes `1a-2a` and an accessory pinned to terminal `1` follows to `1a` (only the terminal-number token of each item is replaced; kinds, part numbers and anything the editor cannot read are kept byte for byte). Level 1 is always the plain `terminal_block_{n}p` id — there is no `_1l` alias, and a stored one is refused as an unknown symbol. **The levels are drawn as columns centred on the instance origin, so the command also shifts the instance's `at` by half the level pitch: level a's terminals stay on exactly the same sheet coordinates**, whatever the block's rotation or mirroring, so a wire already drawn to terminal `1` is still on the same terminal (now called `1a`) after a second level is added instead of being silently re-mapped to the new level or left dangling. One undo restores the `symbol_id` and the position together. Reducing the level count is **refused without touching the drawing** while anything still references a level that would disappear: a wire, a net label, a junction or another symbol's pin sitting on one of its terminals (judged by coordinate coincidence, the same rule the netlist uses — not only by whether the chart calls the terminal a spare), or a jumper, a pin-group range or an accessory naming one of its terminals. The editor predicts those blockers from the chart it already has, lists them under *Levels that would disappear* and disables Apply before the button is pressed; the command re-checks them anyway, so a blocker the editor could not see still cannot change the drawing
  - **Spare terminal insertion** (toolbar *Insert spare* popover: an insertion-point dropdown — the end of the strip, or right after a chosen terminal — a count stepper, and a preview of the resulting symbol id and the new spare terminal's label(s), Apply/Cancel), one `InsertSpareTerminals` command. The new pole (poles, on a multi-level block, one terminal per level) is always added at the **physical end** of the symbol, never in the middle, for the same reason `SetTerminalLevels` shifts `at`: the terminal rows are laid out symmetrically about the instance origin, so growing the pole count would otherwise slide every existing pin to a new sheet coordinate; the command shifts the instance's `at` the opposite way to hold every existing pole exactly where it was, whatever the block's rotation or mirroring. **Only the displayed numbers shift**: every pole after the chosen insertion point has its number pushed up by the inserted count, and the new pole(s) take the vacated number(s) — so inserting after terminal `3` reads in the chart as inserted right after `3` even though the new pole physically sits last on the symbol (chart row order, Number order included, sorts by the *parsed pole number of the displayed label*, not by raw pin position, precisely so an insertion like this lands in the right place; a hand-set `terminal_numbers` override that is not numerically ascending shows the same re-sorted reading). The same command rewrites `attrs["jumpers"]`, any `attrs["pin_groups"]` ranges and `attrs["accessories"]` to the shifted labels, the same way a renumbering does. Refused, without touching the drawing, for a count of zero, a count that would push the pole total past the dynamic symbol family's cap, or an insertion point naming a terminal the block does not have. One undo restores the `symbol_id`, `terminal_numbers` (and any rewritten jumpers) and the position together (a plain `UpdateEntity` back to the pre-insertion snapshot). The popover's **Number handling** radios pick between two modes carried on the command as `renumber_following`: *shift* (default, the behaviour above) and *leave vacant* — the following terminals keep their labels and the spare takes the next free number after the insertion point; if that number is already in use the insertion is refused, with the reason shown in the popover. Labels are handled as a numeric part plus whatever surrounds it, so a strip renumbered with a prefix (`A1`…`A8`) inserts as `A4`/`A9` without losing the prefix, and an insertion point whose label has no digits (such as a terminal named `予備`) is refused instead of guessing. The insertion point is counted in the chart's number order, not in raw pin order, so a second or third insertion — at the end or after any terminal — lands where the grid shows it
  - **Part assignment** (toolbar *Assign part* popover): search the parts database for terminal block parts and assign one; the part number (`value`) and the terminal kind (`attrs["terminal_kind"]`: feed-through / multi-level / fuse / disconnect, from the parts database's `terminal_kind` column, schema v7) are written in one undoable `update_entity`
  - **Accessories** (toolbar *Accessories* popover: a table of position — right before a terminal, or the end — kind — end bracket / partition / end plate — and part number): stored as `attrs["accessories"]` = `terminal:kind:part,…`. The terminal chart shows each accessory as its own row right before its terminal (end ones after the last terminal), and the BOM counts them per part number. A part number not in the parts database only raises a warning in the popover
  - **Inside/outside swap** (toolbar *Swap sides*): flips the selected terminals between swapped and not swapped, stored as `attrs["swapped"]` = a comma list of terminal labels, in one undoable `update_entity`. A swapped terminal shows its inside target, wire and harness on the outside and the other way round, in the editor grid (with a *Swapped* badge), the terminal chart (CSV and sheet) and the terminal connection diagram, which draws its wires on the opposite sides. The combined wire column keeps the inside-then-outside order after the swap. Only the listed terminals change; row order and every other terminal stay as they were. The drawing itself is not rewired: the swap only changes how the block is read
  - **Undo inside the editor**: Cmd+Z / Shift+Cmd+Z (Ctrl on Windows and Linux) undo and redo while the terminal editor is open, and the grid reloads from the drawing; inside a text field the keys keep their usual text-editing meaning
  - **Terminal check**: spare terminals, jumpers pointing at terminals that do not exist, accessory items that cannot be read (a kind other than the three, a terminal the block does not have, or a broken item — reported as a warning, and only that item is skipped), and swap entries naming a terminal the block does not have (a warning; only that entry is ignored)
- **CLI**: `madake terminals [--sheet <ID>]` lists the terminal blocks (reference, poles, level count — blank for an ordinary single-level block —, part number, jumpers, sheet, entity id); `madake export terminal-chart|terminal-diagram <path> [--format csv|pdf] [--terminal <ref|id>]` writes one of them
