# Wire Management

[日本語](05-wire-management.ja.md)

Industrial wiring diagrams live and die by wire data: color, gauge, length, and part numbers. MadakeCAD treats these as first-class wire attributes that flow into reports and verification.

## Available

- **Per-wire attributes**: color (named palette incl. Japanese conventions), gauge in sq (mm²), optional length (m), wire part number, optional net name
- **Wire annotation on the sheet**: every wire prints its own `0.75sq white 0.4m` note, built from the gauge, colour and cut length stored on it. It goes on the wire's longest segment, on the **opposite side from the wire number** (below a horizontal run, right of a vertical one), and a missing attribute is simply left out — a wire with none gets no note. Colour names are translated for print. It has its own view class on screen and is **always** written to SVG and PDF, because on an industrial wiring diagram this is the information the wire is made from
- **Wire part master**: color + gauge → wire part number lookup, stored in the global parts database (with per-meter price and procurement URL); the project file keeps its own snapshot so drawings stay self-contained
- **Wire part number resolution**: a wire's own part number always wins; when it is empty the wire's **colour + gauge** is looked up in the project's wire-part table (the first matching row wins, and an unmatched combination simply stays blank), and the wire list and the from–to report follow. Matching ignores case and surrounding space and treats the English and Japanese names of a colour as the same colour, so a table written `青` resolves a wire drawn `blue`. The table can be imported from CSV (`colour, gauge sq, part number[, note]`, header optional) as **one undoable command**; `POST /api/v1/project/wire-parts/csv` and the `import_wire_parts_csv` IPC call do the same. The properties panel shows the resolved number as *Part number (automatic)*
- **Wire part-number legend block**: an auto-drawn table (Schematic tab → Wiring group → *Wire legend*) with one row per distinct colour+gauge+part-number combination among a sheet's wires — colour, gauge, part number (resolved the same way as above) and the summed length of that combination on that sheet. Rows are sorted by colour then gauge, and the summed length is rounded to two decimals so an inexact binary sum never prints as a long string of digits; a sheet with no wires still draws the header. It holds no content of its own — see [Schematic editor](03-schematic-editor.md) for the full entity description
- **BOM wire roll-up**: the bill of materials adds, after the component rows, one row per wire part number with the project-wide total length, and one `(unassigned)` row for wires whose part number cannot be resolved — see [Standards output](04-standards-output.md)
- **Electrical semantics**: wire gauge and length feed ampacity and voltage-drop verification; terminal blocks provide feed-through connectivity in the netlist
- **Wire numbers**: net-scoped numbers stored on every wire of the net. Automatic numbering (Schematic tab → Wiring group → *Wire numbers*) runs in two modes — *top-up*, which keeps existing numbers and net labels and only fills in unnumbered nets, and *renumber*, which reassigns every automatically generated number; manually typed names are always kept. Numbers are issued top-to-bottom, then left-to-right, are unique across the whole project when no sheet is given, and never collide with a net label. They are drawn on the wire (above a horizontal run, left of a vertical one) and can be edited one net at a time in the properties panel. Same command from the CLI: `madake renumber [--sheet <ID>] [--mode append|renumber] [--start N]`
- **Harness boundaries**: a dashed rectangle with a name (`W1`, `W2` …) and a note, for a group of wires made and bought as one bundle. **An enclosure or case outline is drawn with a graphics rectangle instead** (Schematic tab → Graphics group): a harness around a case would make every conductor merely sitting inside it inherit the case name in the wire list and the terminal chart. Membership is geometric — a wire belongs to the harness that encloses all of its points, and the innermost enclosure wins for nested boundaries. Drawn with the harness tool (Schematic tab → Wiring group → *Harness*, drag a rectangle), edited in the properties panel, which also shows how many wires are enclosed
- **From–to wire list report** (CSV) with sheet, from, to, mate, remark, wire number, color, gauge, length, part number, harness. From and To are the two ends of the wire: a pin is written `reference:pin` (`K1:A1`, `TB1:3`), a net label as its name, an end that touches nothing stays empty; of the two ends the alphabetically smaller one is From, and an unconnected end is always To. **An end that lands on a net label is followed through the net** (excluding this wire's own other end, if it is a pin): when the net has exactly one other pin, the label is replaced with that device's `reference:pin`; otherwise the label stays and the remark column says why: `multi` when the net has several other pins and no single one can be picked, `none` when the net holds no device pin at all so there is nothing to reach (a row where both apply is marked `multi`). Rows are **one per wire**, so two wires that resolve to the same pair of devices — for example the two stubs on either side of a pair of same-named net labels — are two rows that read alike; they are different wires, each with its own colour, gauge and length. **Mate column and net-label resolution are new and are inserted right after To, so the CSV is not compatible with the previous 9-column export** (11 columns now) — a script that reads the wire list CSV by column position must be updated, the same way the terminal chart's Lv column broke its own compatibility
- **Mating connector pairs** (G14): `attrs["mates_with"] = "<designator>"` on a connector instance (the `connector_*` family: dynamic `connector_{n}p` and the static `connector_plug`/`connector_socket` — terminal blocks are not connectors for this purpose) declares one side of a mated pair; declaring it on both sides links the pair fully. ERC (project-wide, since a mate can point at another sheet): a pole-count mismatch between the two connectors is a Warning (`erc.mate_pole_mismatch`), a declaration the other side does not reciprocate is an Info (`erc.mate_one_sided`), and a self-reference or an unknown designator is a Warning (`erc.mate_unknown`). The wire list and from–to report's **mate** column shows the declared mate of whichever end resolves to a device, From side first, so the column reads the same however the wire was drawn. On the drawing, a short dashed line is drawn automatically between the two instances' nearest outline points **only** when both are on the same sheet and within 50 mm of each other (50 mm exactly still counts) — otherwise nothing is drawn and the reports alone carry the pair. On screen the line belongs to the *symbols* view class, since it is drawn between two symbols: hide the symbols and the line goes with them. As with every view class, SVG and PDF export always draw it. Edited from the properties panel (a "Mate" field appears for connector instances) or through any command path. No gender field on the parametric connector family yet
- **Terminal chart**: one table per terminal strip, one row per terminal, in terminal-number order — terminal, **level (Lv)**, internal target, external target, wire number, wire (color, gauge, part number), harness, jumpers. The Lv column carries the level letter of a multi-level terminal block's terminal (e.g. `1a`) and stays blank for an ordinary single-level block. A terminal nothing is wired to is listed as a *spare*. Inside/outside follows panel practice: **a connection on the left-hand pin is the internal (in-panel) side, on the right-hand pin the external side**, judged after rotation. Available as CSV and as a framed drawing sheet. **The Lv column is new and is inserted right after the terminal column, so the CSV is not compatible with the previous 6-column export** (7 columns now, 8 for the project-wide chart) — a script that reads the chart CSV by column position must be updated
- **Terminal connection diagram**: the graphical EPLAN-style form of the same data — the terminal strip runs down the page with **the external side on the left and the internal side on the right**, leader lines to each target, wires of one harness gathered under a named bracket, spare terminals shaded, jumpers drawn as a bar along the strip. For a multi-level terminal block the strip is split into one column per level, headed by the level letter, and each box carries the full level-letter terminal number (`1a`, `1b`, …), so the levels are drawn as the separate columns of terminals they are. One terminal block per page (15 terminals per page, split automatically). PDF only
- **Terminal strip editor** (Reports tab → Terminal blocks group → *Terminal editor*): a grid of the chart rows for the selected terminal block, a toolbar to add/remove **saddle jumpers** between neighbouring terminals and to run the terminal check (spare terminals, jumpers pointing at terminals that do not exist), and footer buttons that generate the chart or the connection diagram. Jumpers are stored on the terminal block symbol as `attrs["jumpers"] = "1-2,3-4"` (each pair written in terminal order — by pole, then by level) and every edit is one `update_entity` command, so Cmd+Z takes it back and the chart, the diagram, the editor and the schematic's own jumper bar all follow. On a multi-level block the spec carries the level letter (`1a-1b` across the levels of one pole, `1a-2a` along one level); a plain numeric spec or a terminal the block does not have is refused by the terminal check rather than silently reported on rows that have no bar. A terminal block's jumpers are also drawn on the schematic symbol itself, the way a saddle jumper sits on a real block: a short thick bar filling the gap between the two terminals' round marks, drawn at more than twice the weight of an ordinary symbol line (the gap is only 1.4 mm wide, so the bar carries no end marks of its own — the edges of the two round marks show where it starts and ends). Sorting, in-place level editing and accessories still need further editor work; a terminal block's level count (1–3) is chosen once, at insertion (part-insert dialog's pole-count stepper gets a matching levels stepper), by placing `terminal_block_{n}p_{levels}l` — the plain `terminal_block_{n}p` id stays the default (1 level) so existing projects are unaffected
- **CLI**: `madake terminals [--sheet <ID>]` lists the terminal blocks (reference, poles, level count — blank for an ordinary single-level block —, part number, jumpers, sheet, entity id); `madake export terminal-chart|terminal-diagram <path> [--format csv|pdf] [--terminal <ref|id>]` writes one of them
